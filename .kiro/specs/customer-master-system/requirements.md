# 顧客マスタ管理システム - 要件定義

## 概要

営業部門の顧客管理と承認ワークフローを実現するシステム。営業担当者が顧客情報を登録・更新し、部長が承認するプロセスを通じて、信頼性の高い顧客マスタデータを構築・維持する。

## ユビキタス言語

### 基本概念
- **顧客（Customer）**: 取引先企業
- **顧客コード（Customer Code）**: システムで自動採番される一意の識別子
- **顧客情報（Customer Information）**: 基本情報、住所、連絡先、口座情報、信用情報を含む企業データ

### 承認ワークフロー関連
- **顧客情報変更申請（Customer Change Request）**: 営業担当者が行った顧客情報の変更依頼
- **担当者変更申請（Assignment Change Request）**: 顧客の担当営業者を変更する申請
- **営業部間担当者変更（Cross-Department Assignment Change）**: 営業部をまたいだ担当者変更
- **承認（Approval）**: 部長による変更申請の承認
- **却下（Rejection）**: 部長による変更申請の却下
- **強制承認（Force Approval）**: システム管理者による強制的な承認処理
- **自己承認制限（Self-Approval Restriction）**: 申請者本人による承認を禁止するルール
- **同時承認（Concurrent Approval）**: 営業部間変更で両方の部長が並行して承認できる方式
- **差分（Diff）**: 変更前後の情報の違い
- **承認期限（Approval Deadline）**: 申請から1週間以内の承認期限

### 信用情報関連
- **信用情報（Credit Information）**: TSRから取得する企業の財務・信用データ
- **信用度（Credit Score）**: 企業の信頼性を示すランク（AAA〜D）
- **支払い信頼性（Payment Reliability）**: 顧客が支払い可能かどうかの判定

### ユーザー関連
- **営業部（Sales Department）**: 顧客管理を担当する組織単位。複数の営業部が存在する
- **営業担当者（Sales Representative）**: 顧客情報を登録・編集する営業部のユーザー
- **担当営業者（Assigned Sales Representative）**: 特定の顧客を担当する営業担当者
- **部長（Department Manager）**: 変更申請を承認する営業部のマネージャー
- **システム管理者（System Administrator）**: システムマスタを管理する情報システム部のユーザー

### 権限・セキュリティ関連
- **アクセス権限（Access Permission）**: ユーザーがデータや機能にアクセスできる範囲
- **更新権限（Update Permission）**: データを変更できる権限
- **承認権限（Approval Authority）**: 変更申請を承認・却下できる権限
- **直接更新権限（Direct Update Authority）**: 承認プロセスを経ずに直接更新できる権限
- **強制処理権限（Force Processing Authority）**: システム管理者の特別な権限
- **監査ログ（Audit Log）**: システムの操作履歴を記録するログ
- **セッション（Session）**: ユーザーのログイン状態を管理する仕組み
- **アカウントロック（Account Lock）**: ログイン失敗時にアカウントを一時的に無効化する機能

### システム連携関連
- **TSR**: 企業信用情報を提供する外部API（将来拡張予定）
- **SAP**: 承認済み顧客情報を連携する基幹システム（将来拡張予定）
- **銀行マスタ（Bank Master）**: システムで管理する銀行・支店情報
- **手動エクスポート（Manual Export）**: データを手動でファイル出力する機能
- **データ同期（Data Synchronization）**: 外部システムとのデータ連携（将来実装予定）

## 要件

### 要件1: ユーザー管理

**ユーザーストーリー**: システム管理者として、各部署のユーザーを管理し、適切な権限を付与したい

#### 受け入れ基準
1. システムは複数の営業部と1つの情報システム部を管理する
2. システムは営業担当者、部長、システム管理者の3つの役割を管理する
3. ユーザーは認証後、役割に応じた機能にアクセスできる
4. ユーザーの作成、更新、無効化ができる
5. 情報システム部のユーザーは営業部の追加、更新、削除ができる
6. 情報システム部のユーザーは営業部に営業担当者を登録することができる
7. 情報システム部のユーザーは営業部に営業担当者の中から複数人を部長に設定できる

### 要件2: 顧客情報管理

**ユーザーストーリー**: 営業担当者として、顧客の詳細情報を登録・管理し、取引の判断材料にしたい

#### 受け入れ基準
1. 営業担当者は新規顧客を登録できる
2. 顧客情報には基本情報、住所情報、連絡先情報、口座情報が含まれる
3. 基本情報には顧客名、業界分類、設立年月日、従業員数、資本金、年商が含まれる
4. 住所情報は本社住所（必須）と支店・営業所住所（無制限）を管理する
5. 連絡先情報は代表連絡先（必須）と担当者情報（無制限）を管理する
6. 口座情報はメイン口座（必須）とサブ口座（最大3件）を管理する
7. 顧客コードはシステムで自動採番される
8. 業界分類は日本標準産業分類に準拠する
9. 顧客情報には担当営業者が紐づけられる
10. 営業担当者は同じ営業部に所属する営業担当者が管理する顧客を一覧で確認できる
11. 情報システム部のユーザーはすべての顧客を一覧で確認できる

### 要件3: 承認ワークフロー

**ユーザーストーリー**: 部長として、営業担当者が登録・更新した顧客情報や担当者変更の内容を確認し、承認・却下を判断したい

#### 受け入れ基準
1. 営業担当者が顧客情報を登録・更新すると、自動的に承認待ち状態になる
2. 営業担当者が担当者変更を申請すると、自動的に承認待ち状態になる
3. 部長は承認待ちの変更申請一覧を確認できる
4. 部長は変更申請の差分（変更前後の比較）を確認できる
5. 部長は変更申請を承認または却下できる
6. 承認権限は申請者と同じ営業部の部長のみが持つ
7. 他の営業部の部長は承認・却下できない
8. 営業部に複数の部長がいる場合、1人の部長が承認すれば十分である
9. 営業部間の担当者変更申請は両方の営業部の部長の承認が必要である
10. 営業部間の担当者変更申請はどちらの部長からでも承認できる（同時承認）
11. 申請者本人が部長の場合でも、自分では承認できず他の部長の承認が必要である
12. 承認時は承認コメントの入力が必須である
13. 却下時は却下理由の入力が必須である
14. 承認期限は全ての申請種別で申請から1週間以内である
15. 承認期限を過ぎた申請は自動的に却下される
16. 承認待ちの顧客は他の営業担当者が編集できない
17. 申請者は承認待ちの申請内容を再編集できる
18. 却下された申請は営業担当者が修正して再申請できる

### 要件4: 通知機能

**ユーザーストーリー**: ユーザーとして、承認プロセスの進捗をタイムリーに把握したい

#### 受け入れ基準
1. 申請時に申請者と同じ営業部の部長にシステム内通知が送信される
2. 承認・却下時に申請者にシステム内通知が送信される
3. 承認期限の1日前と当日に申請者と同じ営業部の部長に催促通知が送信される
4. 通知はシステム内通知のみで、メール通知は行わない

### 要件5: 信用情報管理（将来拡張）

**ユーザーストーリー**: 営業担当者として、顧客の信用情報を確認し、支払い能力を判断したい

#### 受け入れ基準（将来実装予定）
1. システムはTSR APIから顧客の信用情報を自動取得する
2. 信用情報には信用度ランク、信用限度額、財務情報が含まれる
3. 信用情報は定期的に自動更新される
4. 営業担当者は顧客の支払い信頼性を確認できる
5. 信用情報の最終更新日時が表示される

**注記**: 初期バージョンでは信用情報は手動入力とし、将来のバージョンでTSR連携を実装予定

### 要件6: SAP連携（将来拡張）

**ユーザーストーリー**: システム管理者として、承認済みの顧客情報を基幹システム（SAP）に連携したい

#### 受け入れ基準（将来実装予定）
1. 承認済みの顧客情報は自動的にSAPに連携される
2. SAP連携の状況（未連携、連携済み、連携エラー）が管理される
3. SAP連携エラー時は管理者に通知される
4. SAP連携の履歴が記録される

**注記**: 初期バージョンでは手動エクスポート機能とし、将来のバージョンでSAP連携を実装予定

### 要件7: システムマスタ管理

**ユーザーストーリー**: システム管理者として、システムで使用するマスタデータを管理したい

#### 受け入れ基準
1. 情報システム部担当者は銀行マスタを管理できる
2. 銀行マスタには銀行コード、銀行名、支店コード、支店名が含まれる
3. 業界分類マスタは日本標準産業分類に基づいて管理される
4. マスタデータの作成、更新、無効化ができる

### 要件8: 履歴管理

**ユーザーストーリー**: ユーザーとして、顧客情報の変更履歴や承認履歴を確認したい

#### 受け入れ基準
1. 承認・却下の履歴は永続的に保持される
2. 営業担当者は部署内の全履歴を参照できる
3. 部長は部署内の全履歴を参照できる
4. 情報システム部は全履歴を参照できる
5. 却下理由の履歴は全件保持される
6. 履歴には実行者、実行日時、変更内容が記録される

### 要件9: データ整合性

**ユーザーストーリー**: システム管理者として、データの整合性と品質を保ちたい

#### 受け入れ基準
1. 顧客名（正式名称）の重複登録はできない
2. 口座情報は銀行マスタと整合性が保たれる
3. 楽観的ロック（バージョン管理）により競合を制御する
4. 必須項目の入力チェックが行われる
5. データ形式の妥当性チェックが行われる

### 要件10: アクセス権限管理

**ユーザーストーリー**: システム管理者として、適切なアクセス権限を設定し、情報セキュリティを確保したい

#### 受け入れ基準
1. 営業担当者は同じ営業部の全顧客情報を更新（変更申請）できる
2. 営業担当者は自分が担当する顧客の担当者変更を申請できる
3. 担当者変更申請は該当営業部の部長の承認が必要である
4. 営業部をまたいだ担当者変更は両方の営業部の部長の承認が必要である
5. 顧客情報の全項目（基本情報、住所、連絡先、口座、信用情報）は営業担当者と部長で同じように表示される
6. 情報システム部は営業部をまたいだ担当者変更を直接実行できる
7. 部長は同じ営業部内の担当者変更を直接実行できる

### 要件11: システム管理者権限

**ユーザーストーリー**: システム管理者として、システムの安定運用とデータ整合性を保つために必要な権限を持ちたい

#### 受け入れ基準
1. システム管理者は緊急時に顧客情報を承認プロセスを経ずに直接更新できる
2. システム管理者は承認待ちの申請を強制的に承認・却下できる
3. システム管理者は全てのユーザー（他のシステム管理者を含む）を管理できる
4. システム管理者は監査ログ（操作履歴、承認履歴）を参照できるが削除・修正はできない
5. システム管理者が管理できるシステム設定はマスタデータのみである
6. システム管理者の操作は全て監査ログに記録される
7. システム管理者による直接更新や強制処理には理由の入力が必須である

### 要件12: 認証・セッション管理

**ユーザーストーリー**: ユーザーとして、安全で使いやすい認証システムでログインし、適切なセッション管理を受けたい

#### 受け入れ基準
1. システムはユーザーID・パスワード認証を採用する
2. パスワードは8文字以上で英数字混在が必須である
3. ログイン失敗が3回連続すると、アカウントが15分間ロックされる
4. セッションはアクティビティベースで管理され、操作がないと1時間で無効になる
5. 同一ユーザーの複数端末からの同時ログインは制限しない
6. ログイン・ログアウトの履歴は監査ログに記録される
7. セッション有効期限が近づいた場合、ユーザーに警告を表示する
8. 強制ログアウト機能により、システム管理者は特定ユーザーのセッションを無効化できる

## 非機能要件

### パフォーマンス
- 顧客検索のレスポンス時間は3秒以内
- 同時利用者数は最大50名を想定

### 可用性
- 営業時間中（平日9:00-18:00）の稼働率99%以上

### セキュリティ
- ユーザー認証・認可機能
- アクセスログの記録
- 個人情報保護への配慮
- HTTPS通信による暗号化
- 一般的なセキュリティ脆弱性対策（SQLインジェクション、XSS、CSRFなど）

### 運用性
- システム内通知による業務フロー支援
- 履歴管理による監査証跡の確保
- 定期メンテナンス時間は営業時間外（平日19:00-8:00、土日祝日）に実施
- メンテナンス実施時は事前にユーザーに通知する
